ArgoCD is the thing a lot of organisations trust to turn Git into running
workloads across every cluster they own. Its `repo-server` clones your
repositories, renders your manifests, and holds the credentials to do both. So
when I noticed that one of the least interesting fields on a repository - the
proxy URL - flowed unescaped into a shell command, the question wrote itself:
how much do you actually need to be allowed to do before ArgoCD will run your
code for you?

The answer turned out to be very little. `repositories, create` on a single
project - the permission you hand a CI pipeline. No valid SSH key. No repository
that exists. No host that resolves. Not even a completed network connection. The
command runs while the shell is still *parsing* the line.

## Where a proxy becomes a command

When a repository is configured to authenticate over SSH, ArgoCD builds the
environment Git will run in. It wants Git's `ssh` to route through a SOCKS5
proxy if one is set, so it hands `ssh` a `ProxyCommand`. That construction lives
in `util/git/creds.go`, in `SSHCreds.Environ()`:

```go
  ...
  ...
  ...
	// Handle SSH socks5 proxy settings
	proxyEnv := []string{}
	if c.proxy != "" {
		parsedProxyURL, err := url.Parse(c.proxy)
		if err != nil {
			sshCloser.Close()
			return nil, nil, fmt.Errorf("failed to set environment variables related to socks5 proxy, could not parse proxy URL '%s': %w", c.proxy, err)
		}
		args = append(args, "-o", fmt.Sprintf("ProxyCommand='connect-proxy -S %s:%s -5 %%h %%p'",
			parsedProxyURL.Hostname(),
			parsedProxyURL.Port()))
		if parsedProxyURL.User != nil {
			proxyEnv = append(proxyEnv, "SOCKS5_USER="+parsedProxyURL.User.Username())
			if socks5Passwd, isPasswdSet := parsedProxyURL.User.Password(); isPasswdSet {
				proxyEnv = append(proxyEnv, "SOCKS5_PASSWD="+socks5Passwd)
			}
		}
	}
	env = append(env, []string{"GIT_SSH_COMMAND=" + strings.Join(args, " ")}...)
	env = append(env, proxyEnv...)
	return sshCloser, env, nil
```

Two mistakes are stacked here, and each one is harmless on its own.

The first is the quoting. The proxy host is dropped into a single-quoted string
- `ProxyCommand='connect-proxy -S <host>:<port> ...'` - which looks safe until
you remember the attacker controls `<host>`. If the host itself contains a
single quote, it closes ArgoCD's quote, and whatever follows is no longer a
string. It is shell.

The second is where this string ends up. `GIT_SSH_COMMAND` is not passed to a
program as an argument vector. Git runs it through `/bin/sh -c` to launch `ssh`.
So the whole line - including the attacker's host - gets parsed by a shell.
Anything of the form `'$(...)'` closes the quote, runs a command substitution,
and reopens it. The substitution executes during that parse, before `ssh` is
ever spawned, which is why none of the usual SSH preconditions matter.

The same sink is reachable from more than one place. `Repository.proxy` is the
obvious one, but `RepoCreds.proxy` reaches it too - credential templates get
copied onto a repository before the git client is built - and the
`commit-server` used by the hydrator constructs its git client through the exact
same `GetGitCreds` path. One bug, several front doors.

The socks5 proxy support that introduced this landed in January 2024 and shipped
in v2.11.0. It is unchanged on `master` today.

## Building a payload out of a hostname

There is a catch that makes this more interesting than a textbook injection: the
payload has to survive `url.Parse` as a *hostname*. A URL authority cannot
contain a space (it is rejected outright) or a slash (it silently ends the host
and starts the path). A quick sweep of every punctuation character shows what
actually gets through.

```go
package main

import (
      "fmt"
      "net/url"
      "strings"
)

func main() {
      // Probe every punctuation character: does it survive inside a URL host?
      const punct = "'\"$()&;<>*!~][+=,:|?^%{} `\\/@#"

      var survives, blocked []string
      for _, r := range punct {
              c := string(r)
              label := c
              if c == " " {
                      label = "(space)"
              }
              u, err := url.Parse("socks5://a" + c + "b:1080")
              if err == nil && u.Hostname() == "a"+c+"b" {
                      survives = append(survives, label)
              } else {
                      blocked = append(blocked, label)
              }
      }

      fmt.Println()
      fmt.Println("  which characters survive Go's url.Parse host component?")
      fmt.Println()
      fmt.Printf("  SURVIVES : %s\n", strings.Join(survives, " "))
      fmt.Printf("  BLOCKED  : %s\n", strings.Join(blocked, " "))
      fmt.Println()
      fmt.Println("  # spaces and slashes are out - but $ ( ) ; < > = , and ' get through,")
      fmt.Println("  # and base32 (A-Z 2-7 =) is url-safe, so any byte can be smuggled")
      fmt.Println()

      // The entire shell injection is a valid SOCKS5 "hostname".
      payload := "socks5://'$(IFS=,;e=echo,NFSC..2Q==;$e>f;c=base32,-d,f;$c>g;sh<g)':1080"
      u, _ := url.Parse(payload)
      fmt.Printf("  url.Parse(%q).Hostname()\n", "socks5://'$(...)':1080")
      fmt.Printf("    => %s\n", u.Hostname())
      fmt.Println()
}
```

![The result of testing each punctuation character against Go's url.Parse host component](/writing/argo-cd-command-injection-via-proxy-url/charset-bypass.png?size=wide "Command substitution characters survive; spaces and slashes do not")

`$`, `(`, `)`, `;`, `<`, `>`, `=`, `,` and the single quote all pass. Spaces,
slashes, pipes, backslashes and backticks do not. That rules out writing any
normal command directly - `id > /tmp/x` needs both a space and a slash - so the
payload has to be built out of what is left.

Spaces are the easier half. `$IFS` holds the field separator, and every POSIX
shell initialises it to space-tab-newline, so `cd$IFS..` word-splits into
`cd ..` without a space ever appearing in the URL. Slashes are the harder half,
and the answer is that you do not need them: the git process is already running
somewhere inside `/tmp`, so two `cd$IFS..` hops walk up to a writable directory,
and every path after that is relative.

```bash
cd$IFS..;cd$IFS..     # -> cd .. ; cd ..   walks up into /tmp
id>pwned              # -> relative redirect, no slash required
```

That is enough to prove execution. If you want arbitrary bytes - a reverse shell,
a credential sweep - you can smuggle them through base32, whose alphabet
(`A-Z 2-7 =`) is entirely URL-safe, and set `IFS` to a comma yourself so that
word-splitting rebuilds the spaces for you:

```text
socks5://'$(IFS=,;e=echo,<BASE32>;$e>f;c=base32,-d,f;$c>g;sh<g)':1080
```

From there the character restrictions are gone; `g` is a normal shell script.

## Watching ArgoCD assemble the gun

Before pointing this at a live instance I wanted to see ArgoCD build the
dangerous string with its own code, not my reconstruction of it. So I called the
real credential path directly - `Repository.GetGitCreds` -> `NewSSHCreds` ->
`SSHCreds.Environ()` - and printed what it produced.

![ArgoCD's real credential path emitting a GIT_SSH_COMMAND with the attacker's commands outside its own quoting, and git executing it](/writing/argo-cd-command-injection-via-proxy-url/argocd-builds-command.png?size=full "ArgoCD places the attacker's commands, unquoted, outside its own single quotes - and git runs the result through a shell")

There it is, generated by ArgoCD itself on current `master`: the attacker's
`;id>pwned;id;` sitting outside the single quotes of the `ProxyCommand` value.
Hand that environment to `git` the same way `runCredentialedCmd` does and the
commands run - note `bad line length character: uid=`, which is `id`'s output
being fed back into the git protocol stream. A fake key and a hostname that does
not resolve change nothing, because none of that is reached.

## How little it takes to fire

Creating a repository is all it takes to reach this code. `CreateRepository` on
the API server checks exactly one thing before touching your input:

```go
if err := s.enf.EnforceErr(ctx.Value("claims"),
        rbac.ResourceRepositories, rbac.ActionCreate,
        createRBACObject(q.Repo.Project, q.Repo.Repo)); err != nil {
    return nil, err
}
```

`repositories, create` - the permission you would grant a CI pipeline or a
self-service team that is allowed to register their own Git repos. Nothing about
this permission hints that it includes "run commands on the repo-server."

There is a connectivity test on this path, and it is worth being precise about
what it does, because I initially assumed it was the trigger and it is not.
`CreateRepository` calls `testRepo` only for repositories that are *not*
project-scoped, and that test resolves refs with go-git in memory - `git.Init`
over `memory.NewStorage()` - so it never spawns a process and never builds a
`GIT_SSH_COMMAND`. It neither fires the payload nor detects it. Register the
repository against a project and the test is skipped altogether.

What actually execs is manifest generation. The moment any Application points at
the repository, the repo-server builds a real git client and shells out to
`git fetch`. There is a neat accelerant here: `lsRemote` returns immediately if
the revision looks like a commit SHA, so an Application whose `targetRevision`
is 40 hex characters skips ref resolution entirely and goes straight to
`Init()` + `Fetch()`. Point it at a `targetRevision` of
`0123456789abcdef0123456789abcdef01234567` and the payload fires on the
controller's next reconcile.

The credentials are never checked, the host is never reached, and no TCP
connection has to succeed.

The `RepoCreds` variant is worse in one specific way. Registering a *credential
template* runs no connectivity test at all, and ArgoCD copies its `proxy` field
onto any repository whose URL it prefix-matches and which has no inline
credentials of its own. So an attacker can attach a payload to somebody else's
repository and never create an Application at all - the victim's own
reconciliation fires it. Matching is longest-prefix, which also means a longer
prefix quietly wins over an existing legitimate credential set.

## A shell on the repo-server, from a CI token

The interesting question is not whether an administrator can do this. It is which
of the credentials organisations hand out routinely can. ArgoCD's documented way
to delegate to a pipeline is an AppProject role token, scoped to one project, and
`repositories, create` is an unremarkable grant for a pipeline that registers its
own repositories. Policy validation explicitly permits `repositories` as a
project-role resource, so this AppProject is entirely legal:

```yaml
roles:
  - name: deployer
    policies:
      - p, proj:ci:deployer, repositories, create, ci/*, allow
      - p, proj:ci:deployer, applications, create, ci/*, allow
```

I minted a token from that role against a clean v3.3.4 install and used nothing
else. No cluster access, no admin session, no valid key, no reachable host.

![A CI-scoped AppProject role token registering a repository with a malicious proxy and an Application with a 40-hex targetRevision, followed by the injected command's output read out of the repo-server pod](/writing/argo-cd-command-injection-via-proxy-url/ci-token-rce.png?size=full "Two API calls from a project-scoped pipeline token, and the injected command runs as uid 999 in argocd-repo-server")

`uid=999(argocd)`, inside `argocd-repo-server`, seconds after the second API
call. Two requests from a token whose entire authority is one project.

You do not even need cluster access to read the output. Git folds the injected
command's stdout into what it expects to be the ssh transport, chokes on it, and
ArgoCD faithfully reports the whole thing - including the `ProxyCommand` it built
and the command's output - back onto the Application's status:

![ArgoCD reporting the injected ProxyCommand and the executed command's output back through the Application status message](/writing/argo-cd-command-injection-via-proxy-url/status-exfil.png?size=full "bad line length character: uid= - the injected command's stdout, returned through the Application status")

`bad line length character: uid=` is `id` running on the repo-server and its
output being parsed as a git protocol frame. That is a read-anything primitive
delivered over the ArgoCD API.

## Why the repo-server is the wrong place to land

The `repo-server` is one of the most trust-laden components in the cluster:

- **Every repository credential passes through it.** Each manifest request
  carries a full `Repository` object, `sshPrivateKey`, `password` and
  `bearerToken` included. A shell here sits exactly where other tenants' git
  credentials arrive to be used.
- **What it returns becomes what gets applied.** The application-controller
  applies repo-server's output, and its ClusterRole in the shipped manifests is
  `apiGroups: ['*'], resources: ['*'], verbs: ['*']`. If repo-server hands back a
  `ClusterRoleBinding`, the controller is the thing that creates it. This is the
  path to cluster-admin, and the next section walks it end to end.
- **Its own ServiceAccount is not the problem.** There is no Role or RoleBinding
  for it in the base manifests, which is worth saying plainly - the escalation
  comes from the credentials flowing through it and the manifests flowing out of
  it, not from its token. A shell in repo-server has no Kubernetes API rights on
  its own.
- **Egress is unrestricted.** The repo-server NetworkPolicy declares
  `policyTypes: [Ingress]` only, and `REDIS_PASSWORD` is sitting in the container
  environment for lateral reach into the shared cache.

The same credential path is also reachable from `commit-server` via the same
`GetGitCreds` call, which extends the reach to the hydrator's write-back path.

## From a pipeline token to cluster-admin

The shell is not the end of the story, so I ran the rest of it - turning code
execution in repo-server into cluster-admin on the cluster ArgoCD manages.

Start with what the attacker *cannot* do. repo-server's own ServiceAccount has no
RBAC, so the shell can't just call the Kubernetes API. And the escalation can't
come from the pipeline token asking ArgoCD to sync a `ClusterRoleBinding` either:
the token is confined to project `ci`, whose `clusterResourceWhitelist` is empty,
and the controller enforces that whitelist at sync time. The token can't even
reach a sync - `applications, sync` isn't in its grant. Directly, this is a
dead end.

![The pipeline token is confined to a project that permits no cluster-scoped resources, and cannot sync one](/writing/argo-cd-command-injection-via-proxy-url/crb-guardrail.png?size=full "proj:ci:deployer is scoped to project ci, whose clusterResourceWhitelist is empty - a ClusterRoleBinding request is refused")

So the escalation doesn't go through the attacker's own Application. It goes
through what repo-server *produces*: manifests. The application-controller applies
whatever repo-server renders, and its ClusterRole in the shipped manifests is
`apiGroups: ['*'], resources: ['*'], verbs: ['*']`. The whitelist is checked
per-Application, so a poisoned manifest lands as long as it is rendered for *some*
Application in a project that permits cluster-scoped resources. That bar is on the
floor: the built-in `default` project permits everything, and essentially every
real ArgoCD runs at least one auto-syncing "platform" or app-of-apps Application
in a permissive project. In the lab that co-resident app is `platform-bootstrap`,
an ordinary auto-syncing app in `default`, rendering plain directory manifests
from a public repo that the attacker has no rights over. It is the render of
*that* app the attacker has to poison.

Here is the method, and it is a small race. The proxy RCE drops a `perl` implant
and `setsid`-detaches it so it outlives the failed fetch that launched it.
repo-server tries to make writing into another app's checkout hard: every repo's
working tree lives at `/tmp/_argocd-repo/<uuid>`, the parent is not listable, and
each tree is `chmod 0000` at rest, flipped to `0700` only for the few hundred
milliseconds of a render. None of that stops a process running as `argocd`, which
*owns* those directories - it can chmod them back. So the implant learns the live
tree's uuid from the `git` subprocess's `/proc/<pid>/cwd`, then fights the one
real obstacle: before each render, repo-server runs `git clean -ffdx`, which
deletes the planted file, and then reads the directory with a plain `filepath.Walk`.
The manifest only has to *exist at the instant of that walk*. So the implant
rewrites the `ClusterRoleBinding` in a tight loop, and on some reconcile the file
survives from the `clean` to the `Walk`. repo-server renders it as just another
manifest in `platform-bootstrap`'s output, and the controller - holding `*` on
`*` - creates it.

![The RCE implant finds the platform app's checkout via /proc and wins the race against git clean to plant a ClusterRoleBinding; the controller applies it and a kube-system ServiceAccount becomes cluster-admin](/writing/argo-cd-command-injection-via-proxy-url/crb-takeover.png?size=full "The planted ClusterRoleBinding survives a render, its tracking-id names platform-bootstrap as owner, and a kube-system ServiceAccount answers yes to can-i '*' '*'")

The binding's `tracking-id` annotation names `platform-bootstrap` as its owner -
proof the controller created it through a manifest render, not through any API
call the attacker made. And `kubectl auth can-i '*' '*'` for the chosen
`kube-system` ServiceAccount answers `yes`. A token that could not sync a single
cluster-scoped object now owns the cluster, because it could add a repository.
(I removed the binding and the implant afterwards.)

None of this required stealing a session, phishing an admin, or finding a second
bug. It required a pipeline token.

## The fix

The root cause is building a shell command by string concatenation and then
handing it to a shell. Two things close it:

- **Do not interpolate attacker data into a shell string.** The proxy host and
  port should be validated and passed as arguments, never spliced into a quoted
  `ProxyCommand` that a shell will re-parse.
- **Validate the proxy as a proxy.** A SOCKS5 endpoint is a host and a port. A
  value whose "hostname" contains `$`, `(`, `)`, `;` or a quote is not a
  hostname, and rejecting it at the API boundary would have stopped this before
  it ever reached `creds.go`. ArgoCD already has a `ParseProxyUrl` helper, but it
  checks only the scheme and is wired exclusively to cluster proxies - and even
  wired in here it would have let this payload straight through.

The broader lesson is an old one wearing new clothes. `GIT_SSH_COMMAND` is a
shell string, and the instant you `Join` untrusted input into a shell string you
have written a shell injection - it does not matter that the field was "just a
proxy" or that a key was required or that the host was unreachable. The trust
boundary is not the SSH handshake. It is the moment a shell reads the line.

## Disclosure

This was reported to the ArgoCD maintainers with the analysis and a working
proof of concept. Everything above was reproduced end to end against clean
upstream v3.3.4 installs on disposable clusters I control - one on minikube, one
on EKS running Kubernetes 1.36 - and the sink was exercised directly against
`master`. Every token, repository and hostname shown belongs to those labs and
has been destroyed.
